# Производительность и следующий этап

## Что изменено

- Матрица смежности использует индекс рёбер вместо полного поиска рёбер для каждой пары вершин. Подготовка индекса и матрицы имеет сложность O(E + V²). Текстовая матрица и инициализация Флойда используют тот же подход; сам Флойд остаётся O(V³).
- BFS/DFS используют индекс соседей, множество посещённых вершин и компактный журнал: одно событие на посещение. Порядок соседей сохраняется по порядку вершин редактора; для параллельных рёбер сохраняется выбор первого ребра. Построение индекса занимает O(V + E), сортировка соседей добавляет сумму O(d log d). Полные копии пройденного пути для всех шагов больше не хранятся. Отображение отдельного шага ещё восстанавливает префикс пути и перерисовывает Canvas.
- Undo/Redo хранит до 100 XML-снимков с общим бюджетом оценочного содержимого 16 МиБ для обеих сторон истории. Оценка — два байта на символ XML; это не измерение занятой памяти JavaScript.
- Переключение инструмента сохраняет свободный WASM-worker. Текущие вычисления, включая ожидание инициализации, остаются отменяемыми.

Индекс пока создаётся отдельно для операции. Старые плагины могут напрямую менять веса, направления и массивы модели; постоянный кэш требует централизованных команд изменений.

## Измерения

Сравнение перед этим этапом и после него, 2026-11-04: Chromium headless в одной облачной Linux-среде, медиана трёх запусков. Детерминированный ориентированный граф: из каждой вершины идут четыре ребра к следующим вершинам по кольцу, веса 1–4. Создание графа исключено из времени; подготовка BFS включает создание журнала и сообщения, но перерисовка заменена пустой функцией. Это не замер всей отзывчивости редактора или производительности Mac.

| Вершины / рёбра | Матрица до, мс | Матрица после, мс | Подготовка BFS до, мс | Подготовка BFS после, мс |
| --- | ---: | ---: | ---: | ---: |
| 50 / 200 | 1,1 | 0,6 | 38,1 | 0,5 |
| 100 / 400 | 6,9 | 0,8 | 566,4 | 0,5 |
| 400 / 1600 | — | 11,5 | — | 2,1 |
| 1000 / 4000 | — | 60,4 | — | 6,2 |

Большие размеры измерены только после изменений. Малые времена близки к точности таймера; результаты зависят от браузера и нагрузки среды. Графы другой плотности и длинные подписи требуют отдельных замеров.

Для повторения после запуска локального сервера и установки Chromium через Playwright:

```sh
npm run benchmark
# Либо с системным Chromium и другим адресом сервера:
CHROMIUM_PATH=/usr/bin/chromium PLAYWRIGHT_BASE_URL=http://127.0.0.1:8080 npm run benchmark
```

Скрипт проверяет текущую версию на тех же размерах, печатает JSON и ограничивает весь замер 40 секундами. Документы не сохраняются и не публикуются. Исходные цифры до изменений получены тем же способом на предыдущей реализации.

## Что оптимизировать дальше

1. **Автораскладка.** `Graph.VerticesReposition` выполняет до 1000 итераций с попарным взаимодействием вершин в UI-потоке. Следующий этап — вынести расчёт в Worker, добавить отмену, защиту от устаревшего результата и проверку конечности координат. Затем измерить пользу приближённого расчёта сил на больших графах.
2. **Отрисовка и события.** `Application.redrawGraph` перерисовывает весь граф и пересчитывает его тип. Поиск объектов и рёбер во многих местах остаётся линейным. Нужны объединение событий через `requestAnimationFrame`, кэш геометрии/текста и пространственный индекс для выбора объектов. Инвалидация должна учитывать прямые изменения старых расширений.
3. **Модель, история и автосохранение.** Снимки истории всё ещё содержат полный XML. Автосохранение сравнивает документы после сериализации даже при изменении только выделения. Централизованные команды и версии документа позволят сохранять только изменения и безопасно переиспользовать индексы. Для нескольких вкладок нужны отдельные ID документов и обнаружение конфликтов общего черновика.
4. **Начальная загрузка и обновления офлайн-кэша.** Проверить объём предзагрузки исходников/сборок и языковых оболочек; добавить сценарии перехода между версиями приложения, оценить отложенный запуск WASM.
5. **Остальные алгоритмы и платформы.** Перенести тяжёлые JS-вычисления в Worker; сравнить все точные алгоритмы с независимыми эталонами и явно описать эвристики. Проверить Safari/Firefox, реальные Mac и сенсорные устройства. Текущий набор проверяет выбранные сценарии, а не все 25 плагинов.

Обновление jQuery/jQuery UI, PmWiki и CKEditor, переводы новых элементов и эксплуатация публичного сервера остаются отдельными задачами из [плана модернизации](modernization.md). Переход серверной части с PHP на другой язык пока не устраняет найденные задержки браузерного редактора; приоритет — модель TypeScript и вычисления вне UI-потока.
